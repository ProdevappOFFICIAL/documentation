Most Jetic issues fall into a handful of predictable categories: scan configuration problems, AI provider errors, workflow token injection failures, and environment mismatches. This page covers the most common issues and how to resolve them. If your problem isn't listed here, check the GitHub issues tracker linked at the bottom of this page.

<AccordionGroup>

  <Accordion title="jetic scan finds no routes">
    If `jetic scan` completes but reports `0 endpoints`, the scanner could not locate any Express route registrations in your source.

    **Things to check:**

    - **Is your project TypeScript?** Jetic uses ts-morph to parse `.ts` files. JavaScript-only projects (`.js` files) are not supported.
    - **Is there a `tsconfig.json` in your project root?** Jetic looks for TypeScript configuration in the current working directory. Run `ls tsconfig.json` to confirm it exists.
    - **Do your routes use standard Express syntax?** Jetic recognizes `app.get()`, `app.post()`, `router.get()`, `router.post()`, and similar Express Router methods. Custom wrappers or decorators may not be detected.
    - **Are you running `jetic scan` from the project root?** The scanner starts from `process.cwd()`. Running from a subdirectory causes it to miss routes defined elsewhere in the tree.

    ```bash
    # Confirm you're in the right directory
    ls tsconfig.json package.json src/
    jetic scan
    ```
  </Accordion>

  <Accordion title="Endpoints are missing parameters or request body schemas">
    Jetic discovers routes statically, but extracting parameter names, types, and request body shapes requires the AI analysis phase. If endpoints appear in `jetic inspect` output but show no parameters or body fields in `model.json`, the AI step may have failed silently or produced incomplete results.

    **Things to check:**

    - **Verify AI is configured:** Run `jetic config` and confirm that `AI Provider`, `AI Model`, and `API Key Env Var` are all set to non-empty values.
    - **Confirm the API key is available:** Check that the environment variable named in `apiKeyEnvVar` is actually set in your shell or `.env` file:
      ```bash
      # If apiKeyEnvVar is OPENROUTER_API_KEY:
      echo $OPENROUTER_API_KEY
      ```
    - **Try a more capable model:** Simpler models may struggle with complex middleware chains or unusual validation patterns. Upgrade to `gpt-4o` for better extraction:
      ```bash
      jetic config ai --provider openai --model gpt-4o --key-env OPENAI_API_KEY
      jetic scan
      ```
    - **Fill in manually:** You can edit `.jetic/model.json` directly to add `parameters` and `requestBody` fields for any endpoint the AI missed.
  </Accordion>

  <Accordion title="Workflow steps are returning 401 Unauthorized">
    A `401` on a protected endpoint during a workflow run almost always means a token wasn't captured correctly, or wasn't injected into the right header.

    **Step-by-step diagnosis:**

    1. **Check that the login/auth step passed.** Jetic stops the entire workflow if an auth step fails. Look at the terminal output — did Step 1 (or whichever step produces your token) show a green ✓?

    2. **Verify the `capture` path matches your actual response.** Open `.jetic/workflow.json` and find the step that produces the token. Check the `capture` field:
       ```json
       "capture": {
         "workflow:accessToken": "data.accessToken"
       }
       ```
       If your login endpoint returns `{ "token": "eyJ..." }` (not nested under `data`), the path should be `"token"`, not `"data.accessToken"`. Run `jetic memory` after the workflow to see what was actually captured.

    3. **Verify the `inject` key matches the captured key exactly.** In the protected step, the memory key in `inject` must be the same string that was used in `capture`:
       ```json
       "inject": {
         "header:Authorization": "Bearer {{workflow:accessToken}}"
       }
       ```
       A mismatch — for example, capturing as `"workflow:token"` but injecting `"workflow:accessToken"` — causes the lookup to return nothing, sending the request with no Authorization header.

    4. **Clear memory and retry.** Stale tokens from a previous run can cause confusion. Run:
       ```bash
       jetic simulate workflow --workflow .jetic/workflow.json --clear-memory
       ```
  </Accordion>

  <Accordion title="model.json not found error">
    If Jetic prints an error like `No model.json found. Run jetic scan first.`, the behavioral model doesn't exist yet or Jetic is looking in the wrong directory.

    **Things to check:**

    - **Run `jetic scan` first.** The `model.json` file is generated by the scan command and does not exist until you run it at least once.
    - **Run commands from your project root.** Jetic resolves `.jetic/` relative to `process.cwd()`. If you run `jetic inspect` from a subdirectory like `src/`, it looks for `src/.jetic/model.json` which doesn't exist. Always run Jetic commands from the same directory as your `tsconfig.json`:
      ```bash
      cd /path/to/my-express-app
      jetic scan
      jetic inspect
      ```
    - **Check that `.jetic/model.json` exists:**
      ```bash
      ls .jetic/
      ```
  </Accordion>

  <Accordion title="AI analysis failing or API key errors">
    If `jetic scan` or `jetic simulate workflow` fails with an error about a missing or invalid API key, the key isn't reaching Jetic at runtime.

    **Things to check:**

    - **Confirm your `.env` file contains the correct variable.** Open `.env` and verify the variable name matches exactly what's in `config.json`:
      ```bash
      cat .env
      # Should contain: OPENROUTER_API_KEY=sk-or-...
      ```
      ```bash
      cat .jetic/config.json
      # "apiKeyEnvVar" should be "OPENROUTER_API_KEY"
      ```
    - **Check for typos in the variable name.** Variable names are case-sensitive. `OPENROUTER_API_KEY` and `openrouter_api_key` are different names.
    - **Confirm the key value is valid.** Test it with a direct curl or API call to the provider to rule out an expired or revoked key.
    - **Re-run `jetic init`** to reset the config and re-enter your key:
      ```bash
      jetic init
      ```
  </Accordion>

  <Accordion title="Jetic Studio not loading">
    If `jetic dev` starts without error but the browser shows a blank page or connection refused, the dashboard server may be running on a different port or something else is already using the default port.

    **Things to check:**

    - **Check for port conflicts.** By default, Jetic Studio runs on port `8787`. If another process is using that port, the server fails to bind. Try an alternate port:
      ```bash
      jetic dev --port 9000
      ```
    - **Open the URL manually.** If your browser didn't open automatically, navigate to `http://localhost:8787` (or your chosen port) directly.
    - **Check the terminal for error output.** If the port is already in use, Jetic prints an error. Identify the conflicting process:
      ```bash
      # macOS / Linux
      lsof -i :8787
      ```
    - **Confirm `model.json` exists.** Jetic Studio reads from `.jetic/model.json` on startup. Run `jetic scan` first if the file doesn't exist.
  </Accordion>

  <Accordion title="TypeScript compilation errors during scan">
    If `jetic scan` fails with TypeScript errors or ts-morph diagnostic messages, there's a configuration issue with your project's TypeScript setup.

    **Things to check:**

    - **Ensure `tsconfig.json` exists in your project root.** Jetic passes your `tsconfig.json` to ts-morph for project configuration. Without it, ts-morph creates a default project that may not include all your source files.
    - **Check that your project compiles independently.** Run `tsc --noEmit` to see if there are pre-existing TypeScript errors. Jetic cannot scan a project that has compilation errors in the files it needs to analyze.
    - **Avoid overly strict compiler settings.** Some `strict` mode flags can surface errors in third-party type definitions that ts-morph reports as diagnostics. If you encounter this, try setting `"skipLibCheck": true` in your `tsconfig.json`.
    - **Ensure source files are included.** Check that your `tsconfig.json` `include` or `exclude` patterns don't accidentally exclude your route files.
  </Accordion>

  <Accordion title="Workflow generates the wrong steps or misses endpoints">
    If the AI-generated `workflow.json` describes the wrong sequence, uses incorrect paths, or misses important endpoints, the generation prompt may need more context or the goal description may be too vague.

    **Things to check:**

    - **Make your `--goal` more specific.** Instead of `"test user flow"`, try `"User registers with email and password, logs in, creates a product listing, then deletes it"`. More detail gives the AI clearer instructions about which endpoints to include and in what order.
    - **Use `--generate-only` to review before executing.** Generate the workflow first, inspect `.jetic/workflow.json`, make any corrections, then run it manually:
      ```bash
      jetic simulate workflow --goal "User buys a product" --generate-only
      # Edit .jetic/workflow.json as needed
      jetic simulate workflow --workflow .jetic/workflow.json
      ```
    - **Re-scan with a better AI model.** The quality of the generated workflow depends on the endpoint metadata in `model.json`. If endpoints lack summaries or parameter details, switch to a more capable model and re-scan:
      ```bash
      jetic config ai --provider openai --model gpt-4o --key-env OPENAI_API_KEY
      jetic scan
      jetic simulate workflow --goal "Your goal here"
      ```
    - **Edit `workflow.json` directly.** The workflow file is plain JSON — you can add, remove, or reorder steps, fix paths, and adjust `capture` / `inject` mappings by hand.
  </Accordion>

</AccordionGroup>

## Getting Help

If you've worked through the steps above and still can't resolve your issue, open a GitHub issue with your error output, your `jetic config` output (redact API key values), and a description of your project structure:

[https://github.com/jeticlabs/Jetic/issues](https://github.com/jeticlabs/Jetic/issues)
